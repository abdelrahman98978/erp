خطة منع الخلط بين قواعد البيانات والمستخدمين والبيانات داخل ERP
Khalid Group ERP — Data, User, Tenant & Environment Isolation Blueprint
الغرض من هذا المستند هو وضع قواعد تقنية وتشغيلية صارمة تمنع اختلاط بيانات شركات المجموعة أو مستخدميها أو ملفاتها أو تقاريرها أو جلساتها أو سجلاتها، سواء بسبب خطأ برمجي أو صلاحية زائدة أو ربط غير صحيح بين قواعد البيانات.
1. المبدأ الأساسي: لا توجد بيانات مشتركة افتراضياً
• كل شركة تعامل كنطاق مستقل Tenant/Company Scope، ولا يجوز لأي استعلام أو خدمة أو تقرير العمل دون تحديد نطاق الشركة صراحة.
• هوية المستخدم شيء مستقل عن عضويته داخل الشركات. امتلاك حساب واحد لا يعني امتلاك الوصول لكل الشركات.
• أي بيانات مشتركة بين شركات المجموعة يجب أن تكون معرفة كـ Shared Master Data ومصرحاً بها صراحة، ولا يتم اعتبارها مشتركة تلقائياً.
• يجب أن يكون المنع على مستوى الخادم وقاعدة البيانات، وليس فقط عبر إخفاء القوائم من الواجهة.

4. قواعد إلزامية لكل جدول
• كل جدول أعمال Business Table يحتوي tenant_id وcompany_id كحقول غير قابلة لأن تكون NULL.
• الجداول التابعة ترث company_id من السجل الأب ولا تسمح بتغييره من طلب المستخدم.
• يمنع وجود سجل بدون مالك شركة واضح.
• المفاتيح المركبة والـForeign Keys يجب أن تمنع ربط سجل من شركة A بسجل من شركة B.
• لا تستخدم أسماء الشركات أو البريد أو أسماء الفروع كمرجع أمني؛ الاعتماد يكون على IDs ثابتة.
• أي جدول Shared يجب أن يحمل تصنيفاً واضحاً shared_scope ولا يختلط بالجداول التشغيلية.

6. فصل المستخدم عن الشركة
يكون users جدول هوية مركزي فقط، بينما صلاحية المستخدم الفعلية تأتي من memberships. مثال: المستخدم U100 قد يملك Membership في شركة A كمدير موارد بشرية، وMembership أخرى في شركة B كقارئ فقط. لا يجوز حفظ role_id واحد مباشر داخل users لأنه يسبب خلط الصلاحيات بين الشركات.

7. سياق الجلسة Session Context
• بعد تسجيل الدخول لا تعتمد الجلسة على user_id فقط.
• يجب أن تحتوي الجلسة الفعلية على active_membership_id وactive_company_id وallowed_branch_ids وallowed_department_ids.
• عند تغيير الشركة يتم إنشاء/تحديث Context جديد وإعادة جلب البيانات من الصفر.
• يمنع تمرير company_id من الواجهة واستخدامه مباشرة دون التحقق من Membership.
• أي Token قديم يجب ألا يحتفظ بصلاحية لشركة تم سحب الوصول منها.
8. Row-Level Security ومنع Cross-Tenant Leakage
كل SELECT/INSERT/UPDATE/DELETE يجب أن يمر بسياسة عزل. المبدأ: record.company_id يجب أن يطابق active_company_id، وأن تكون Membership نشطة، وأن يمتلك المستخدم Permission المطلوبة.
العملية
التحقق الإلزامي

company_id + branch/department scope + permission

توليد company_id من الخادم وليس من المستخدم

صلاحية حذف مستقلة + Audit

9. منع الخلط في الـ API
• كل Endpoint يعرف Resource + Action + Company Scope قبل تنفيذ Business Logic.
• الـBackend لا يثق بـ company_id أو user_id أو role المرسل من Frontend.
• يتم استخراج الهوية من Token ثم استخراج Membership من قاعدة موثوقة.
• الاستعلامات Repository/ORM يجب أن تستخدم Scoped Query تلقائياً.
• يمنع استخدام Service Role أو Admin Database Client داخل Endpoints العادية.
• أي Internal API بين الخدمات يجب أن يحمل Service Identity وScope واضحين.

11. منع الخلط في التقارير ولوحات المؤشرات
• كل Dashboard يجب أن يبدأ بفلتر company_id إلزامي على الخادم.
• تجميع المجموعة Group Consolidation يكون في Dataset منفصل مخصص للإدارة العليا.
• لا تستخدم Cache مشتركة دون إدخال company_id في Cache Key.
• CSV/Excel/PDF exports تحمل اسم الشركة ونطاق التقرير.
• Scheduled Reports ترسل فقط لمستلمين لديهم Membership نشطة في نفس النطاق.
• أي AI Analytics أو BI Model يجب أن يستقبل بيانات مصفاة حسب الشركة قبل التحليل.

13. منع الخلط في السجلات المحاسبية
• Chart of Accounts يمكن أن يكون Template مشتركاً، لكن الحساب الفعلي Ledger Account يحمل company_id.
• كل Journal Entry يجب أن يحتوي company_id ثابتاً لكل بنوده.
• يمنع Journal متعدد الشركات في نفس القيد.
• البنوك والصناديق ومراكز التكلفة والعملاء والموردون إما خاصة بالشركة أو معرفة بوضوح كـ shared master مع mapping مستقل.
• التسلسلات Invoice Number / Voucher Number / PO Number تكون منفصلة لكل شركة.
• أي Consolidation بين الشركات يتم بعد الترحيل إلى طبقة Consolidation وليس داخل دفاتر الشركات الأساسية.
14. منع الخلط في الموارد البشرية
• Employee Number لا يعتبر Global Identifier؛ يستخدم employee_id داخلي + company_id.
• ملف الموظف والراتب والعقد والإجازات والحضور مرتبطة بعضوية الشركة.
• نقل الموظف بين شركتين ينشئ Assignment/Membership جديداً ويحافظ على السجل التاريخي.
• الرواتب لا تظهر لموظفي HR غير المخولين حتى داخل نفس الشركة.
• المرفقات الشخصية تحفظ في مسارات معزولة ولا تدخل في Global Search.
15. منع الخلط في الإشعارات والبريد
• كل Notification يحمل company_id وmembership_id.
• القوالب Templates قد تكون مشتركة، لكن المتغيرات والبيانات المرسلة تأتي من نطاق الشركة الحالية.
• يمنع إرسال تقرير أو فاتورة لشخص اعتماداً على email فقط؛ يتم التحقق من علاقته بالسجل.
• روابط البريد تكون Signed Deep Links وتعيد التحقق من الصلاحية عند فتحها.

17. النسخ الاحتياطي والاستعادة
• توثيق الشركة ضمن Backup Metadata.
• اختبار Point-in-Time Recovery دون فقد عزل tenant.
• عند استعادة شركة واحدة إلى بيئة مؤقتة، يجب إزالة أو إخفاء بيانات الشركات الأخرى.
• تشفير النسخ الاحتياطية وإدارة مفاتيح التشفير مركزياً مع صلاحيات محدودة.
18. Audit Logs وسجل الوصول
يسجل النظام: user_id، membership_id، company_id، branch_id، action، resource، record_id، timestamp، IP، device، result، previous_value وnew_value عند الحاجة. ويجب تسجيل محاولات الوصول إلى شركة أو سجل خارج النطاق حتى لو تم منعها.
19. قواعد عدم الخلط في البرمجة
• لا يوجد function مثل getAllInvoices() في طبقة المستخدم؛ بل getInvoices(context).
• لا يتم بناء Query ثم إضافة company filter اختيارياً؛ الفلتر يكون جزءاً أساسياً من Repository.
• لا تستخدم متغير global للشركة الحالية على الخادم.
• لا يتم الاعتماد على UI state لتحديد Tenant.
• لا تكتب SQL JOIN بين جداول أعمال دون شرط تطابق company_id عندما يكون ذلك مطلوباً.
• تضاف Automated Tests لأي Endpoint جديد قبل الدمج.

21. اختبارات قاعدة البيانات
• Foreign Key/Constraint يمنع ربط سجلين من شركتين مختلفتين.
• RLS Test Suite تنفذ كحسابات حقيقية وليس Database Owner.
• اختبار SQL Injection وIDOR وHorizontal Privilege Escalation.
• اختبار أن Service Accounts لا تستطيع الوصول إلا للـSchemas/جداول المطلوبة.
• اختبار Migration على بيانات متعددة الشركات لضمان عدم فقد tenant_id.

23. التعامل مع المورد أو العميل المشترك
إذا تعامل نفس المورد مع أكثر من شركة، لا يتم إنشاء سجل مالي عالمي واحد. يمكن وجود master_party مركزي للبيانات العامة، ثم company_vendor_account لكل شركة يحتوي شروط الدفع والرصيد والضرائب والحسابات والبنك والتقييم والعقود الخاصة بتلك الشركة.
24. الخدمات المشتركة Shared Services
• المحاسب المركزي لا يمنح وصولاً عاماً؛ يملك Membership منفصلة لكل شركة.
• يمكن إنشاء Portal للخدمات المشتركة يعرض قائمة الشركات المصرح بها فقط.
• كل معاملة تبدأ باختيار الشركة ثم يتم تثبيت Context حتى انتهاء العملية.
• لا يسمح بتنفيذ Bulk Action عبر شركات متعددة إلا في وظيفة مخصصة ومدققة.

26. إجراءات عند اكتشاف خلط بيانات
• إيقاف المسار/الخدمة المتسببة فوراً.
• إلغاء الجلسات أو Tokens ذات العلاقة.
• تحديد السجلات والمستخدمين المتأثرين من Audit Logs.
• منع التعديل على الأدلة وسجلات الحادث.
• إصلاح Policy/Query ثم تشغيل Regression Tests.
• فحص ما إذا تم عرض أو تصدير أو إرسال بيانات خارج النطاق.
• توثيق Root Cause وإضافة اختبار آلي يمنع تكرار الخطأ.

28. شرط القبول النهائي
لا يعتبر النظام آمناً لمجموعة متعددة الشركات إلا إذا كان تغيير أي Company ID أو User ID أو Record ID أو URL أو Request Parameter غير قادر على إظهار بيانات شركة أخرى. يجب أن يكون العزل قائماً في قاعدة البيانات والـBackend والتخزين والكاش والبحث والتقارير والـQueues معاً، وأن يكون الوصول المتعدد للشركات استثناءً مصرحاً به وليس الوضع الافتراضي.
