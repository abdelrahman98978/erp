1. الملخص التنفيذي ونطاق التكامل
الهدف هو أن يصبح ERP هو مركز التشغيل الداخلي الوحيد للشركة، بينما تبقى مساند القناة النظامية المعتمدة للعمليات التي تتطلب تنفيذًا أو توثيقًا داخل المنصة. لا ينبغي بناء تكامل يكرر قواعد مساند أو يتجاوزها؛ بل طبقة تكامل ثنائية الاتجاه تحفظ رقم الطلب والعقد والتأشيرة والدفعة والحالة الرسمية، وتربطها بقيود ERP التشغيلية والمالية.
• إنشاء سجل موحد للعميل، الطلب، العامل، العرض، العقد، التأشيرة، الدفع، التأمين، الشكوى ونقل الخدمة.
• استقبال أي طلب/تحديث وارد من مساند وإسقاطه مباشرة على حالة داخل ERP.
• إرسال العمليات المسموح بها من ERP إلى مساند بعد التحقق من الصلاحيات والبيانات.
• منع الإدخال المكرر وتعارض الحالات عبر Idempotency Keys وExternal IDs.
• توليد القيود المحاسبية والتسويات آليًا من أحداث العقد والدفع والاسترداد.
• إتاحة لوحة متابعة تشغيلية تربط كل مرحلة بزمن SLA والمسؤول عنها والتنبيهات.
• حفظ سجل تدقيق غير قابل للتعديل يثبت من قام بماذا، ومتى، وما الطلب والاستجابة.
2. ما هو مؤكد رسميًا عن مساند
وفق المصادر الرسمية المتاحة حتى 31 أغسطس 2026: منصة مساند منظومة رقمية لخدمات العمالة المنزلية، وهي القناة المعتمدة لتوثيق العلاقة بين شركات/مكاتب الاستقدام وأصحاب العمل وتنفيذ عمليات الاستقدام. الدليل العام يوضح دخول الشركات عبر نظام الدخول الموحد للوزارة، وجود لوحة بيانات للشركات، الدفع الإلكتروني، الإشعارات، قائمة الطلبات والتحقق اللحظي من المدخلات. كما توجد بوابة مستقلة باسم «بوابة تكامل مساند».

3. مبادئ التصميم وحدود المسؤولية
• System of Record: مساند للحالة النظامية الرسمية؛ ERP للسجل التشغيلي والمالي الداخلي.
• Zero Trust Integration: كل طلب بين النظامين موقّع/موثق، وكل صلاحية بأقل امتياز.
• Event-driven first: تحديث الحالات عبر Webhook/Event إن توفر، مع Polling reconciliation احتياطي فقط.
• Idempotent by design: كل عملية قابلة لإعادة الإرسال دون تكرار النتائج.
• Never overwrite silently: أي تعارض يذهب إلى Queue للمراجعة مع حفظ النسختين.
• PII minimization: لا نخزن إلا البيانات اللازمة، مع تشفير الحقول الحساسة.
• Tenant isolation: كل شركة/فرع/مكتب له نطاق بيانات وصلاحيات منفصل داخل ERP.
• Auditability: كل تغيير حالة، إعادة إرسال، استثناء، تعديل يدوي أو تسوية له سجل مستقل.
4. المعمارية التقنية المستهدفة

7. إدارة العروض والعقود
• استقبال العرض وربطه بطلب الاستقدام والعميل والفرع.
• تخزين السعر الأساسي، الضريبة، التذكرة الداخلية إن وجدت، الرسوم، الإجمالي والمهلة.
• تنبيه قبل انتهاء صلاحية العرض بمدد قابلة للضبط.
• عند قبول العرض: إنشاء حدث ContractAcceptancePending ثم انتظار تأكيد مساند.
• بعد الدفع/التفعيل: تثبيت نسخة العقد المرجعية وعدم السماح بتعديل قيمها يدويًا إلا عبر عملية تصحيح موثقة.
• تخزين hash لملف العقد/المستند إن كان تنزيله متاحًا، لإثبات عدم تغييره.
• إدارة حالات الإلغاء والاسترداد عبر workflow منفصل، وعدم حذف العقد أو الدفع من قاعدة البيانات.

9. العمالة والسير الذاتية والترشيح
• Worker Master مستقل عن Candidate Profile لتجنب خلط الشخص بالترشيحات المتعددة.
• نسخة Snapshot من السيرة المستخدمة وقت العرض حتى لا يؤدي تعديل السيرة لاحقًا إلى تغيير ما قبله العميل.
• Deduplication عبر مجموعة مؤشرات: passport hash + date of birth + nationality، بحسب ما يسمح به النظام واللوائح.
• حالات: Available / Reserved / Offered / Selected / Contracted / Visa Processing / Arrived / Transferred / Inactive.
• قفل الحجز Reservation Lock لمنع تقديم نفس العامل لأكثر من عميل في نفس اللحظة إذا كان النموذج التشغيلي يتطلب الحصرية.

11. التأمين والضمانات
• ربط وثيقة التأمين بالعقد والعامل والعميل.
• حالات Policy: Quoted / Issued / Active / Claimed / Expired / Cancelled.
• فتح Claim Workflow عند تحقق حالة تستدعي مطالبة، مع مستندات وإثباتات وسجل زمني.
• عدم اعتبار التأمين بديلًا عن إدارة الشكوى أو الالتزام التعاقدي.
• مؤشرات: نسبة العقود المؤمّنة، زمن إصدار الوثيقة، عدد المطالبات، معدل قبول المطالبات وقيم التعويض.

18. المطابقة والمزامنة وإدارة التعارض
• Near-real-time: Webhooks للأحداث إذا كانت متاحة.
• Incremental sync: مزامنة التغييرات منذ آخر cursor/timestamp.
• Nightly reconciliation: مطابقة الطلبات المفتوحة والعقود والمدفوعات والتأشيرات.
• Financial reconciliation: كل يوم مع settlement sources المتاحة.
• Full audit reconciliation: أسبوعي/شهري لعينة أو كامل السجلات حسب الحجم.
• Conflict precedence: الحالة الرسمية من مساند لا تُستبدل يدويًا، لكن يمكن وضع Internal Override Flag لأغراض التشغيل دون تغيير Official Status.
• كل تعارض ينتج record في integration_conflicts مع owner وseverity وresolution.

25. الاختبارات والـSandbox
لا يبدأ الإنتاج قبل توفير بيئة اختبار أو بيانات اختبار معتمدة من مساند إن كانت متاحة، وتوثيق السيناريوهات التالية.
• Happy path كامل: طلب → عرض → قبول → دفع → عقد → تأشيرة → إكمال.
• رفض العرض وانتهاء المهلة.
• فشل الدفع ثم النجاح.
• Refund جزئي/كامل إن كان مدعومًا.
• رفض التأشيرة وإعادة التقديم.
• تكرار نفس الطلب بنفس idempotency key.
• Webhook مكرر، متأخر، out-of-order، وتوقيع خاطئ.
• انقطاع مساند لمدة 30 دقيقة مع استمرار إدخال الأعمال في ERP.
• عودة الخدمة وتصريف Queue دون مضاعفة العمليات.
• Credential rotation.
• تغيير schema غير متوافق.
• اختبار عزل Tenant: مستخدم شركة A لا يرى أي external refs لشركة B.
• اختبار صلاحيات المالية مقابل العمليات.
• مطابقة مالية على 100+ عملية تجريبية.
• اختبار أحمال حسب الحجم المتوقع ×3.
• DR restore واختبار إعادة بناء حالة التكامل من Event Store.

29. قائمة التحقق للحصول على اعتماد الربط
• ☐ تحديد الكيان القانوني/المنشأة المرخصة التي سيتم الربط باسمها.
• ☐ الحصول على جهة الاتصال التقنية/التشغيلية الرسمية في مساند.

• ☐ تحديد طريقة Authentication: OAuth2/mTLS/API Key/SSO أو غيرها رسميًا.
• ☐ تحديد IP allowlisting ومتطلبات الشهادات.
• ☐ تحديد Webhook URL requirements والتوقيع وإعادة الإرسال.
• ☐ تحديد Rate Limits وTimeouts وRetry policy.
• ☐ تحديد Error Codes وBusiness Validation Codes.
• ☐ تحديد Data Retention واستخدام البيانات.
• ☐ تحديد Production onboarding، UAT sign-off، Go-live window، Support escalation.

33.2 قاعدة ذهبية لمنع الخلط
• أي سجل متعلق بمساند يجب أن يحمل tenant_id وcompany_id وmusaned_connection_id وexternal_reference.
• لا يقبل Backend قيمة company_id من واجهة المستخدم دون التحقق منها من Session/Token وصلاحية المستخدم.
• لا يمكن لمستخدم شركة 1 اختيار اتصال مساند شركة 2 حتى لو عرف المعرف التقني.
• كل Credential أو Certificate أو Webhook Secret يربط بكيان قانوني واحد، ما لم تنص وثائق مساند رسميًا على اتصال متعدد المنشآت.
• كل قيد محاسبي ناتج عن مساند يرحل إلى Ledger الشركة صاحبة العقد فقط.
• لوحة المجموعة لا تستخدم سجلات خام مشتركة دون Row-Level Security؛ التجميع يتم عبر طبقة تقارير محكومة.

35.1 قواعد Constraints إلزامية
• Unique(company_id, musaned_external_request_id) لمنع تكرار نفس طلب مساند داخل الشركة.
• Unique(connection_id, external_event_id) لمنع تكرار Webhook.
• Foreign Key يضمن أن connection.company_id = entity.company_id.
• Foreign Key يضمن أن contract.company_id = payment.company_id = settlement.company_id.
• Check يمنع تغيير company_id لسجل بعد إنشائه؛ النقل بين الشركات ليس Update بل عملية Migration نظامية منفصلة إن كانت مسموحة.
• كل query تشغيلية تضيف company_id تلقائيًا من Security Context، وليس من form input.

42. سيناريو منع كارثة خلط الشركات
مثال: موظف يعمل في RC01 يحاول — بقصد أو خطأ — إرسال طلب باستخدام connection_rc02. يجب إيقاف العملية في أكثر من طبقة:
• واجهة المستخدم لا تعرض connection أصلًا للمستخدم التشغيلي.
• API يستنتج company_id من session.
• Integration Service يقرأ connection الافتراضي المربوط بـcompany_id.
• Policy Engine يتحقق من connection.company_id == session.company_id.
• قاعدة البيانات ترفض FK/constraint غير المتطابق.
• Adapter يضيف establishment scope من connection registry فقط.
• Audit يسجل محاولة التلاعب/التعارض ويرفع Security Alert إذا كانت متكررة.

44. استراتيجية Queue متعددة الشركات
لمنع شركة ذات حجم مرتفع أو خطأ متكرر من تعطيل الشركات الأخرى، يوصى بواحد من نموذجين: queues منفصلة لكل شركة، أو queue مشتركة مع partitions حسب connection_id. عند استخدام Queue مشتركة يجب تطبيق fair scheduling وحدود retry مستقلة.
• Partition Key = connection_id أو company_id.
• DLQ منفصل منطقيًا لكل شركة.
• Rate Limit Counters لكل connection.
• Circuit Breaker لكل connection؛ لا يفتح circuit لكل النظام بسبب شركة واحدة.
• Metrics تحمل company_id label مع منع PII.

47. قائمة Go-Live لكل شركة
• ☐ تم التحقق من الاسم القانوني والسجل والترخيص وربطها بـcompany_id الصحيح.

• ☐ تم تجهيز rollback/circuit breaker.

49. قرار معماري موصى به
للنظام الحالي الذي يضم أربع شركات استقدام، التصميم الموصى به هو: Shared ERP + Shared Integration Platform + Isolated Tenant Data + Isolated Musaned Connections + Isolated Ledgers + Group Read-Only Consolidation. هذا يحقق الاستفادة من كود واحد وصيانة واحدة، مع منع خلط الهوية القانونية والتشغيلية والمالية للشركات.
ولا يتم تثبيت أسماء endpoints أو auth flows لمساند على أنها نهائية إلا بعد استلام وثائق بوابة التكامل الرسمية لكل منشأة. عندها يتم تحديث Musaned Adapter وMapping Registry فقط، بينما تبقى بنية الشركات الأربع والصلاحيات والمحاسبة والـaudit كما هي.
